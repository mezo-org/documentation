Este inicio rápido se sigue de principio a fin. Al terminar, habrás pagado
$0.001 en MUSD en Mezo Testnet a tu propio servidor vendedor Express local
usando los SDK `@x402/*`, con la interfaz de navegador `@x402/paywall`, lista para usar,
haciendo todo el trabajo del lado del cliente, de modo que escribes **cero código de cliente**.

Para el contexto conceptual de qué es x402, empieza por la [descripción general de x402](../).

## Qué vas a construir

Un servidor Express de un solo archivo cuya **ruta raíz `/`** está protegida por un
pago en MUSD:

- Un **navegador** que accede a `/` sin pagar recibe `HTTP 402 Payment Required`
  con la interfaz incluida de `@x402/paywall`: la conexión de la billetera, el pago y el reintento
  se gestionan por ti.
- Un **cliente programático** (`curl`, `fetch`, un agente de IA) recibe el mismo
  `402` con un cuerpo JSON compacto y los requisitos de pago legibles por máquinas
  en un encabezado de respuesta `PAYMENT-REQUIRED`.
- Una vez liquidado un pago de $0.001 en MUSD, la ruta se desbloquea y devuelve su
  respuesta JSON.

El servidor que construyes es **exactamente el mismo código** que ejecuta la demo alojada en
[`https://demo.vativ.io/`](https://demo.vativ.io/): primero pagarás a la instancia
alojada para comprobar la configuración de tu billetera (paso 3) y después levantarás y pagarás
la tuya (pasos 4–6).

## Requisitos previos

- **Node.js 20+** y **pnpm 9+** en tu equipo.
- Una extensión de billetera del navegador compatible con redes EVM (MetaMask, Rabby,
  Coinbase Wallet o cualquier billetera que exponga un proveedor EIP-1193).
- **Un SDK `@x402` actualizado.** La compatibilidad con Mezo viene incluida en los registros predeterminados:
  Mainnet desde `@x402/evm` v2.15.0 / Go v2.15.0 / Python v2.13.0 (2026-06-12),
  y Testnet desde versiones anteriores. Este inicio rápido fija la versión `2.16.0`, la que
  ejecuta la demo alojada. Consulta la
  [referencia de x402 en Mezo](../#referencia-de-x402-en-mezo) para ver la matriz completa.
- **~20–30 minutos.** Obtener MUSD de testnet implica una entrega del faucet + una
  transacción de préstamo; hazlas pronto (pasos 1–2) y estarán listas
  cuando las necesites.

<Aside type="tip" title="Usarás dos cuentas: Buyer y Merchant">
El inicio rápido usa **dos cuentas distintas** en la misma billetera:

- **Account A — Buyer (comprador).** Tiene MUSD y paga las solicitudes a la API.
- **Account B — Merchant (comerciante).** Recibe los pagos.

Usar dos cuentas hace que cada pago se vea en el explorador como una
transferencia de A a B, que es la forma más sencilla de confirmar tu configuración
de principio a fin. Ninguna de las cuentas necesita saldo en BTC para los pagos x402
en MUSD, ya que el facilitador paga el gas en nombre de ambas partes (aunque
necesitarás BTC para realizar el flujo opcional de préstamo de MUSD que se describe más abajo).
</Aside>

## Paso 2: Obtén MUSD de testnet para pagar

En testnet, MUSD se **acuña, no se obtiene de un faucet**: lo pides prestado
contra BTC de testnet.

<Aside type="caution" title="Préstamo mínimo único">
Abrir un préstamo requiere una deuda mínima de **2,000 MUSD** (1,800 de principal +
200 MUSD de depósito de gas). Es un mínimo del protocolo, no un costo por prueba:
pides prestado una vez y reutilizas el saldo en muchas solicitudes de pago. A
`$0.001` por llamada, un solo préstamo cubre unos dos millones de
pagos de prueba.
</Aside>

Selecciona **Account A (Buyer)** en tu billetera antes de empezar, para que todos
los fondos del paso 2 vayan a Account A. Account B (Merchant) permanece vacía todo el tiempo.

   [faucet de Mezo](https://faucet.test.mezo.org) o en el canal `#testnet`

</Steps>

La página del token MUSD en el explorador también es útil si quieres

## Paso 4: Instala los paquetes de x402

Crea un proyecto nuevo para tu propio vendedor:

```bash
mkdir mezo-x402-quickstart && cd mezo-x402-quickstart
pnpm init
pnpm add @x402/core@2.16.0 @x402/evm@2.16.0 @x402/express@2.16.0 @x402/paywall@2.16.0 express@^4.19.2
pnpm add -D typescript tsx @types/express@^4.17.21 @types/node
```

Las versiones de `@x402/*` están fijadas en `2.16.0`, la versión que ejecuta la demo
alojada, para que lo que construyas coincida con lo que ya pagaste en el paso 3.
Las versiones más recientes en general también funcionan; consulta la
[matriz de compatibilidad de los SDK](../#compatibilidad-de-los-sdk) para ver las versiones mínimas por red.

<Aside type="note" title="Sobre los valores predeterminados de pnpm init">
`pnpm init` genera un `package.json` con `"main": "index.js"` y sin
`"type": "module"`. Nada de eso importa aquí: ejecutarás `server.ts` mediante
`tsx`, que gestiona ESM y CommonJS sin configuración.
</Aside>

<Aside type="note" title="Las advertencias de peer dependencies son normales">
`pnpm` puede mostrar advertencias amarillas de peer dependencies durante la instalación (por
ejemplo `Issues with peer dependencies found`, o avisos sobre los rangos de versión peer de
`@x402/*`). Son informativas y puedes
ignorarlas sin problema en este inicio rápido: la instalación se ha completado siempre que los
dos comandos `pnpm add` terminen con `0`. Si un error real detiene la instalación,
`pnpm` lo muestra en rojo y termina con un código distinto de cero.
</Aside>

## Paso 5: El vendedor, en un solo archivo

El vendedor conecta tres piezas: un `HTTPFacilitatorClient`
que se comunica con el facilitador, un `x402ResourceServer` con el
esquema de pago EVM `"exact"` registrado para Mezo Testnet, y la
interfaz incluida de `@x402/paywall` como proveedor del paywall. Después, la llamada a
`paymentMiddleware` protege `GET /` con un precio de $0.001.

Crea `server.ts` dentro de `mezo-x402-quickstart/` exactamente con este
contenido; es el archivo fuente del servidor de la demo, literal:

```typescript
/**
 * Mezo x402 Quickstart — the out-of-box @x402/paywall smoke test.
 *
 * Run this server and open http://localhost:4021/ in a browser: the
 * @x402/paywall UI renders. That is the smoke test. The root route `/` is
 * protected by the x402 payment middleware, so an unpaid browser GET returns
 * HTTP 402 with the paywall; paying $0.001 in MUSD unlocks a success response.
 *
 *   Network:     Mezo testnet — eip155:31611 (CAIP-2)
 *   Asset:       MUSD  0x118917a40FAF1CD7a13dB0Ef56C86De7973Ac503  (18 decimals)
 *   Price:       $0.001 (PRICE env overrides)
 *   Facilitator: https://facilitator.vativ.io  (verifies + settles payments)
 *
 *   pnpm install
 *   pnpm exec tsx server.ts    (monorepo: pnpm --filter mezo-x402-quickstart start)
 */
import express from "express";
import { paymentMiddleware, x402ResourceServer } from "@x402/express";
import { ExactEvmScheme } from "@x402/evm/exact/server";
import { HTTPFacilitatorClient } from "@x402/core/server";
import { createPaywall } from "@x402/paywall";
import { evmPaywall } from "@x402/paywall/evm";

// --- Config (override any of these via environment variables) --------------
const PORT = Number(process.env.PORT ?? 4021);
const NETWORK = "eip155:31611"; // Mezo testnet
const PAY_TO = process.env.PAY_TO ?? "0xC3376296a18ef364eA19287203EEd7a87f18e738";
const FACILITATOR_URL = process.env.FACILITATOR_URL ?? "https://facilitator.vativ.io";
const PRICE = process.env.PRICE ?? "$0.001";

const app = express();

// The facilitator verifies and settles x402 payments. The resource server
// registers the "exact" EVM payment scheme for our network. @x402/evm already
// knows Mezo testnet, so a plain "$0.001" price resolves to MUSD automatically.
const facilitator = new HTTPFacilitatorClient({ url: FACILITATOR_URL });
const resourceServer = new x402ResourceServer(facilitator).register(
  NETWORK,
  new ExactEvmScheme(),
);

// The out-of-box @x402/paywall browser UI, scoped to EVM networks.
const paywall = createPaywall().withNetwork(evmPaywall).build();

// Protect the ROOT route. A browser GET / with no payment renders the paywall.
app.use(
  paymentMiddleware(
    {
      "GET /": {
        accepts: {
          scheme: "exact",
          price: PRICE,
          network: NETWORK,
          payTo: PAY_TO,
        },
        // No trailing period: the paywall appends ". To access this content, ...".
        description: `Mezo x402 Quickstart — pay ${PRICE} in MUSD to unlock`,
      },
    },
    resourceServer,
    { appName: "Mezo x402 Quickstart", testnet: true },
    paywall,
  ),
);

// Unlocked content — served only after a payment settles.
app.get("/", (_req, res) => {
  res.json({ ok: true, message: "Paid! You unlocked the Mezo x402 Quickstart." });
});

app.listen(PORT, () => {
  console.log(`Mezo x402 Quickstart listening on http://localhost:${PORT}/`);
  console.log("Open it in a browser to see the @x402/paywall UI.");
});
```

Recorriéndolo de arriba abajo:

- **Bloque de configuración.** Todo lo que depende del entorno es una
  constante que se puede sobrescribir con una variable de entorno. `PAY_TO` toma por defecto la dirección receptora de la demo alojada
  (la misma `0xC337…e738` que viste en la comprobación del explorador del paso 3) y
  la sobrescribirás con **tu Account B** en el paso 6. El precio también es una
  constante: `PRICE` (por defecto `$0.001`) se usa tanto en los requisitos de pago
  como en el texto del paywall, así que sobrescribirlo (p. ej.,
  `PRICE='$0.005'`) cambia el precio de la ruta de principio a fin.
- **`HTTPFacilitatorClient` + `x402ResourceServer`.** El facilitador en
  `facilitator.vativ.io` verifica y liquida los pagos; el servidor de
  recursos registra el esquema EVM `"exact"` para `eip155:31611`. Una simple
  cadena en dólares `price: "$0.001"` se resuelve a la cantidad correcta de MUSD en
  tiempo de ejecución, sin dirección de token en tu código.
- **`createPaywall().withNetwork(evmPaywall).build()`.** La interfaz de
  navegador incluida, limitada a redes EVM. Sin este proveedor, el
  middleware recurre a un stub que formatea las cantidades como USDC de 6 decimales
  y muestra un marcador de posición "Install @x402/paywall".
- **`paymentMiddleware(...)`.** Protege `GET /`. El tercer argumento es
  la configuración del paywall: `appName` se convierte en el título de la página y
  `testnet: true` muestra la indicación del faucet `Need Mezo USD on Mezo Testnet?`
  que viste en el paso 3.
- **La ruta desbloqueada.** El manejador simple `app.get("/")` solo se ejecuta
  después de que el middleware haya verificado y liquidado un pago.

(Técnicamente podrías establecer `PAY_TO` en Account A y pagarte a ti mismo, pero
entonces un pago correcto no se vería onchain: el MUSD sale de A y llega
a A, así que el saldo del token no cambia. Dos cuentas te dan una señal clara
de antes/después en el explorador).

## Paso 6: Ejecuta tu vendedor y págale tú mismo

<Aside type="caution" title="Primero comprueba si hay un vendedor obsoleto en el puerto 4021">
Si algún proceso ya está escuchando en `localhost:4021` (por ejemplo, un
`tsx server.ts` anterior que olvidaste detener), las comprobaciones siguientes pasarán porque
respondió el **otro** proceso, no el tuyo. Los pagos realizados en el navegador
irán entonces al `PAY_TO` con el que se configuró ese servidor obsoleto,
no al que acabas de establecer. Este fallo se ve exactamente igual que un éxito; la
única señal de que algo va mal es que tu terminal no muestra registros de solicitudes
mientras que la de otro sí.

Termina cualquier proceso obsoleto que esté escuchando antes de continuar:

```bash
lsof -i :4021          # No output = port is free, skip the kill
kill $(lsof -ti :4021) # If the command above printed anything, run this
```

Como alternativa, usa otro puerto: el servidor lo lee del
entorno, p. ej., `PORT=5001 PAY_TO=0x… pnpm exec tsx server.ts`.
</Aside>

Cambia tu billetera a **Account B (Merchant)**, copia su dirección `0x…`
e inicia el servidor con esa dirección como dirección receptora:

```bash
PAY_TO=0xYOUR_ACCOUNT_B_ADDRESS_HERE \
  pnpm exec tsx server.ts
```

<Aside type="caution" title="No omitas PAY_TO">
El servidor arranca sin problemas sin `PAY_TO`: recurre a la dirección receptora
de la demo alojada. Todos los pagos que hagas irán entonces al comerciante
de la demo en lugar de a tu Account B, y la ejecución "funciona" mientras tu
comprobación en el explorador del paso 6 de más abajo sigue vacía. Tampoco hay ninguna validación
de formato: una dirección con un error tipográfico se usa tal cual sin aviso. Copia la dirección
directamente desde tu billetera.
</Aside>

Deberías ver `Mezo x402 Quickstart listening on http://localhost:4021/`.
El middleware ahora intercepta las solicitudes sin pagar a `/`. Lo que recibe un cliente
depende de cómo se identifica: un **navegador** (un encabezado
`Accept: text/html` más un `User-Agent` de navegador) recibe la página
HTML completa del paywall; **todo lo demás** (`curl`, `fetch`, `httpie`, un agente
de IA) recibe un cuerpo JSON compacto con los requisitos de pago
codificados en Base64 en un encabezado de respuesta `PAYMENT-REQUIRED`. En ambos casos, no
se necesita código del lado del cliente.

<Steps>

1. Comprueba que el servidor responde con `402`:

   ```bash
   curl -s -o /dev/null -w "%{http_code}\n" http://localhost:4021/
   # Expect: 402
   ```

   (La **interfaz** del paywall solo se muestra en un navegador; ese es el siguiente
   paso. `curl -i` sobre la misma URL muestra el estado `402` junto con el
   encabezado `PAYMENT-REQUIRED`, que lleva los requisitos de pago
   legibles por máquinas; decodifícalo con `base64 -d` para ver los mismos
   scheme/network/amount/payTo que declara la configuración de tu ruta).

2. Abre `http://localhost:4021/` en el mismo navegador que usaste para
   la prueba rápida con la demo en vivo del paso 3. **Cambia a Account A (Buyer)**
   antes de conectarte: es la cuenta que tiene MUSD.

3. Se carga el paywall: la misma interfaz que en el paso 3, pero ahora servida por tu
   propio código:

     src={paywallLocalInitial}

   />

4. Conecta Account A, confirma **Mezo Testnet (chain ID `31611`)**,
   haz clic en **Pay now** y firma la autorización en tu billetera.

5. El paywall reintenta la solicitud. Cuando el facilitador liquida
   onchain, se muestra la respuesta JSON desbloqueada:

   ```json
   { "ok": true, "message": "Paid! You unlocked the Mezo x402 Quickstart." }
   ```

6. Verifica la transferencia de A → B onchain. Abre ambas pestañas del explorador:

## Pasar a mainnet

Todo lo anterior se ejecuta en Mezo Testnet. Llevar el mismo vendedor a Mezo
Mainnet (`eip155:31612`) es un **cambio de una sola línea**: un SDK actualizado resuelve por ti el
token MUSD de mainnet y el proxy de liquidación canónico, y el
facilitador es el mismo endpoint.

En `server.ts`, cambia la constante de red:

```diff
-const NETWORK = "eip155:31611"; // Mezo testnet
+const NETWORK = "eip155:31612"; // Mezo mainnet
```

| Qué | Testnet → Mainnet | ¿Requiere cambios? |
|---|---|---|
| `NETWORK` (CAIP-2) | `eip155:31611` → `eip155:31612` | **Sí: la línea de arriba** |
| `PAY_TO` | tu dirección de testnet → tu dirección de mainnet | **Sí: establécelo siempre explícitamente en mainnet** |
| Activo MUSD | lo resuelve el SDK en ambas redes | No: `DEFAULT_STABLECOINS` lo asigna |
| URL del facilitador | `facilitator.vativ.io` en ambas redes | No: el mismo facilitador atiende ambas |
| Proxy de liquidación | canónico en ambas redes | No: el SDK lo resuelve automáticamente |

<Aside type="caution" title="Mainnet mueve fondos reales">
Los pagos en mainnet liquidan **MUSD real**, y el facilitador paga el gas con **BTC real**;
no hay faucet. Establece `PAY_TO` en una dirección que controles en
mainnet (el valor predeterminado integrado es la dirección de la demo: en mainnet, no establecer
`PAY_TO` significa pagarle a otra persona con dinero real). Prueba primero con un `price`
bajo y deposita en el lado receptor solo lo que pienses
transaccionar.
</Aside>



## Solución de problemas

| Síntoma | Causa | Solución |
|---------|-------|-----|
| `does not provide an export named 'DEFAULT_STABLECOINS'` en tiempo de ejecución | Una dependencia transitiva fija `@x402/paywall`/`@x402/evm` en una versión anterior a la que necesita tu red de destino (Mainnet necesita `≥ 2.15.0`; Testnet, `≥ 2.10.0`) | <details><summary>Fuerza ambos a una versión actual mediante los overrides de tu gestor de paquetes</summary><br/>**pnpm**: añade a `package.json` (en el nivel superior, junto a `dependencies`) y luego ejecuta `pnpm install`:<br/>```<br/>"pnpm": { "overrides": { "@x402/paywall": "^2.16.0", "@x402/evm": "^2.16.0" } }<br/>```<br/>**npm**: `"overrides": { ... }` en el nivel superior y luego `npm install`.<br/>**yarn**: `"resolutions": { ... }` y luego `yarn install`.<br/>Sobrescribe ambos paquetes a la vez: `@x402/paywall` importa `DEFAULT_STABLECOINS` de `@x402/evm`.</details> |
| El paywall muestra `$10000000000.00` en lugar de `$0.001` | Igual que arriba: un `@x402` antiguo formatea MUSD como USDC de 6 decimales | <details><summary>La misma solución: fuerza `^2.16.0` mediante overrides</summary><br/>Consulta la fila anterior para ver el fragmento completo (variantes de `pnpm` / `npm` / `yarn`).</details> |
| `install` falla al resolver `@solana/kit@6.10.0` → `@solana/keys@6.10.0` (no hay versión coincidente) | `@x402/paywall` trae un SDK de Solana transitivo cuya versión `6.10.0` hace referencia a subpaquetes aún no publicados (un hueco temporal en el proyecto original). Los vendedores que solo usan EVM nunca usan el paywall de Solana, pero la dependencia se resuelve igualmente durante la instalación | Fija la última versión correcta mediante un override y vuelve a instalar: **npm** `"overrides": { "@solana/kit": "6.9.0" }` en el nivel superior; **pnpm** `"pnpm": { "overrides": { "@solana/kit": "6.9.0" } }`; **yarn** `"resolutions": { "@solana/kit": "6.9.0" }` |
| `EADDRINUSE: address already in use :::4021` | Otro proceso está usando el puerto 4021 | Ejecuta `lsof -i :4021` para encontrar qué proceso lo ocupa, o usa un puerto libre: `PORT=5001 PAY_TO=0x… pnpm exec tsx server.ts` |
| `tsx: command not found` | La dependencia de desarrollo `tsx` no se instaló, o el comando se está ejecutando fuera del directorio del proyecto | Vuelve a ejecutar `pnpm add -D tsx` dentro del proyecto; invócalo como `pnpm exec tsx server.ts` |
| `SyntaxError` en `import` / errores de sintaxis de TS desde Node | Usas Node.js &lt; 20 | Actualiza a Node.js 20+ (compruébalo con `node --version`) |
| La billetera pide cambiar de red / el pago nunca se confirma | La billetera está en la red de Mezo equivocada | Confirma que la billetera está en el chain ID que espera el vendedor (`31611` para Testnet, `31612` para Mainnet) |
| Se devuelve `402 Payment Required` pero la interfaz del paywall nunca se muestra | La cadena `network` no es un identificador CAIP-2 | Usa exactamente `'eip155:31611'` o `'eip155:31612'`; tanto `'mezo-testnet'` como `31611` a secas se rechazan |
| La billetera se niega a añadir "Mezo Testnet", o la añade pero los saldos / transacciones no cuadran | Se introdujo el chain ID en hexadecimal (p. ej., `0x7A5B`) cuando el campo de la billetera espera decimal, o se usó el chain ID de Mainnet (`31612`) cuando querías Testnet | Introduce el chain ID en decimal: **`31611`** para Testnet (`31612` para Mainnet). La URL de RPC también debe apuntar a testnet (`https://rpc.test.mezo.org`): un chain ID de testnet con un RPC de mainnet produce, sin avisar, una red que parece real pero no contiene nada |
| Todo "funciona", pero Account B nunca recibe MUSD | No se estableció `PAY_TO` (el servidor recurre sin avisar a la dirección receptora de la demo alojada) o la dirección tenía un error tipográfico; no hay validación de formato | Detén el servidor y reinícialo con `PAY_TO=0x…` copiado directamente de la Account B de tu billetera; vuelve a revisar el explorador después del siguiente pago |
| El facilitador devuelve `unsupported network` | Se sobrescribió `FACILITATOR_URL` con un facilitador sin compatibilidad con Mezo (p. ej., `x402.org/facilitator`) | Elimina `FACILITATOR_URL`: el valor predeterminado integrado `https://facilitator.vativ.io` atiende ambas redes de Mezo |
| El paywall se carga pero **Pay now** nunca liquida, sin errores | La billetera no tiene MUSD, o el MUSD está en la red equivocada | Vuelve al paso 2; confirma que el contrato del token MUSD de testnet muestra saldo |
| La demo del paso 3 (demo.vativ.io) nunca liquida | El mismo problema de billetera/MUSD/red; aíslalo aquí antes de pasar al paso 4 | No te saltes la prueba rápida del paso 3; corrige la parte de la billetera antes de escribir código del servidor |
| El pago se firma en la billetera, pero el facilitador lo rechaza / la verificación falla | El **name** del dominio EIP-712 del activo se definió a mano de forma incorrecta | El name del dominio EIP-712 de MUSD es **`Mezo USD`** (versión `1`), **no** el símbolo `MUSD`; una discrepancia hace fallar la verificación de la firma. Deja que el SDK lo proporcione mediante `getDefaultAsset`, o establece exactamente `name: "Mezo USD", version: "1"` si construyes tú mismo los metadatos del activo |
| Si ejecutas tu propio facilitador/liquidador: fallos intermitentes en la estimación de gas en Mezo | La estimación de gas en Mezo necesita un pequeño margen | Aumenta el límite de gas / el multiplicador de estimación en el firmante. No te encontrarás con esto si usas el `facilitator.vativ.io` alojado, que ya lo tiene en cuenta |
